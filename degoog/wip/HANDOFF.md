**Read PLAN.md first: its work order overrides the "Next" section below. M1 (morning preview) comes first.**

The spec is the user's handoff text (they paste it into each new chat). These notes cover only what has been decided or verified since then.

## Decisions (made with the user)
- AI spot: reserve a fixed 3-line clamp + ⌄ expand; if the AI fails, the same box shows "AI summary unavailable" (same size, so no shift).
- Network answers (Wikidata, ESPN, endoflife.date): cache them in RAM only, under a hashed key, with the same 12 h TTL as degoog's engine cache. Never written to disk; gone on restart. This is so repeat searches have the answer ready before paint.
- Public suffix list: 76 KB even in tree form (data/psl.enc via enc.py), and degoog doesn't compress pages. So it ships as a versioned static file loaded with `defer` before the ct-inline module, cached immutable; it is not inlined. Before using it, verify which public path degoog serves statically (check src/server for serveStatic or a public dir). The user's blocker only rejects /api/plugin/ and GET /api/command.
- v50 ships to main once, when every test passes. WIP lives on branch v50-wip under degoog/wip/.
- Parallel help: only self-contained research goes to background helpers. All code stays in the main chat, for consistency.

## M2 design (verified in degoog e006d50 source, 2026-11-23 06:05 UTC; not built yet)
- degoog already filters server-side, before results render: `domainBlockList` (Hide; matches the host and its subdomains; needs domainBlockEnabled) and `domainScoreList` lines `host|N` (N added to each result's score; scores are ~1-10 per engine x multiplier, +5 per extra engine, so a top result is ~60). Lists live in dataDir/search/search-lists.json (src/server/utils/filtering/domain-lists.ts, createListStore; writeList publishes an invalidate, so the filter re-reads at once).
- Plan: the four choices map onto degoog's own lists, so Hide/Prefer/Lower work server-side on every tab and before paint, with no list shipped to the page: Hide = domainBlockList; Prefer = `host|100`; Lower = `host|-100`; Normal = removed from both. The user's existing Block/score entries become the starting state (block -> Hide, score > 0 -> Prefer, < 0 -> Lower). One list in Settings.
- Writes must keep degoog's settings auth (the bridge via /api/command is unauthenticated; anyone reaching the instance could change the list). Stock menu: POST /api/settings/domain-action with header x-settings-token = sessionStorage token (result-actions.ts _getToken/TOKEN_KEY), guarded by settingsAuth (gandalfAtTheGate; refuses cross-site). It only appends block / upserts score, it can't remove a block line. Found (src/server/routes/settings/general/instance.ts): GET /api/settings/general (settingsAuth) returns settings + domain lists (through trimBigFields: check it doesn't cut long lists), and POST /api/settings/field {key: "domainBlockList" | "domainScoreList", value: whole list text} (settingsAuth, settingsLock, writeListField -> writeDomainList -> invalidate). So the page does read-modify-write of both lists with the x-settings-token header. No token or 401 (not signed in to Settings in this browser session) -> the menu says so and links to Settings; nothing is written. The iPhone blocker only rejects /api/plugin/ and GET /api/command, so /api/settings/* is reachable.
- The page still needs the list for "Prefer = no 2-per-site cap" and to show the current choice in the menu: read-only copy kept in localStorage `ct-sites` (refreshed from a read-only bridge route each page load and on every change), same pattern as `ct-show`. core planPage already takes sites {domain: prefer|lower|hide} (tests exist).
- Anti-SEO "auto" marks: the plugin's own file (/app/data/plugins/clean-titles/sites-auto.json: domain -> {strikes, seen, auto}); auto only ever writes Lower, and any manual choice for a domain stops auto for it.
